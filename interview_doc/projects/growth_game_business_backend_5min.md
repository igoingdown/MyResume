# 商城增长技术优化 - 业务后端 5min 版本

  • 口语稿（约 5min）

我用一个“商城增长技术优化”的项目来讲我在业务后端这块的能力，这个项目我从立项、方案设计到落地和迁移都深度参与，最后把增长玩法从一个个孤立的烟囱式系统，提升成一套可复用、可配置、可灰度、可回滚的统一框架。

先用三句话说清楚背景和痛点：第一，在 24–25 年这段时间，随着签到、报销机、爆券、全额免单、付费券包等十多个玩法陆续上线，业务的核心矛盾从“有没有玩法”变成了“能不能规模化复用、能不能持续快迭代”。第二，不同玩法的配置化能力差异很大，配置做得好的玩法，一周可以开多轮实验拿 ROI 数据；配置差的玩法，一个月才能迭代一次，很难在预算和人力上持续投入。第三，多玩法并行各自为战，代码风格和架构完全不统一，复用差、维护成本高，新玩法建设周期长，上线风险也大。

在这样的背景下，我给自己的目标是：通过统一框架，把“玩法搭建”和“策略投放”工程化，既要提高研发效率和业务试错效率，又要把稳定性风险控制住。具体做法我拆成三层：协议统一 → 链路统一 → 代码范式统一。

第一层是协议统一，也是整个项目风险最高的一步。简单说，就是前后端交互都要收敛到一套统一的 API 和数据结构上。我没有简单地在原有协议上硬加字段，而是从页面承接的本质出发，把页面抽象成“页面 + 多个区块”的模型：页面负责承接玩法，区块对应资源位，比如任务引导区块、用户资产展示区块、商品 feed 区块等。协议里我定义了一部分稳定的核心字段，保证所有玩法都能理解，另一部分通过扩展字段和版本机制来承载玩法个性化需求。同时，我为协议设计了版本治理策略，支持灰度发布、版本兼容和快速回滚，避免统一协议变成一次性大手术。

第二层是链路统一，分为 B 端和 C 端两块。B 端我做了一轮模型抽象，把运营日常要操作的对象沉淀成几类数据模型：玩法组件模板/实例、策略组件模板/实例、规则引擎和投放计划。玩法组件更多抽象前端样式和交互数据结构，策略组件抽象算法策略、任务和频控等数值策略，投放计划就是“某个组件实例 + 一套规则”，通过这些模型，运营可以用同一套后台去搭建不同玩法，统一配置投放策略。C 端则主要做了四件事：承接统一协议的页面和区块渲染、沉淀可复用组件链路（比如 feed 、资产展示、领奖链路）、定义组件级的数据交互协议（SPI）、以及把规则引擎的决策接入到渲染和交互里。

第三层是代码范式统一，我在框架内部大量使用了工厂模式、责任链模式、上下文编排等设计模式，搭建了高性能的流程编排引擎。用工厂模式去生成不同类型的组件实例，用责任链实现规则引擎的多步决策和拦截，用 ctx 模式实现一个请求在各个组件之间的有序流转和扩展。这一层工作不直接给业务看到，但它决定了后续新玩法能不能在统一范式下快速接入，而不是再长出一棵新的“旁路树”。

上面是整体设计，接下来我重点说三个面试官通常会追问的难点：

第一个难点是协议统一的兼容性和演进风险。统一协议不是简单地改一版结构，而是在多玩法并存、历史包袱和多个前后端团队的约束下，既要避免一次性大改，又要留出足够的扩展性。我在设计时做了两件事：一是区分稳定核心字段与可扩展字段，核心字段几乎不动，扩展字段通过版本和 feature flag 来管理；二是配套了灰度和回滚机制，每次协议演进都从小流量、少玩法开始，结合监控和线上 diff 去观察行为差异，确认安全之后再扩面。

第二个难点是配置化带来的规则复杂度和“防配错”。随着配置能力增强，运营在一个资源位上可以配置的人群、实验、时间窗口、优先级和各种自定义因子越来越多，很容易出现规则冲突、覆盖关系不清晰甚至互相打架的问题。我没有把这件事当作“运营自己对齐”，而是把“防配错”当成规则引擎的一等公民：在规则模型层面预先支持冲突检测和优先级裁决；在平台层面提供上线前的预览校验、模拟流量 dry-run、版本对比和可追溯审计；在运行时配合灰度和快回滚机制，一旦发现不合理的行为可以快速降级和回滚到上一版本。

第三个难点是迁移的平顺性和整体稳定性保障。我们不可能停服重构，所以我采用的是“配置模型双写 + diff SDK + dry-run + 分层灰度 + 线上对账”的迁移路径。先在老系统与新框架之间做模型双写，让同一份配置同时在两套链路下生成决策结果，通过 diff SDK 去对比行为差异；再通过 dry-run 把新框架的输出打到旁路，用监控和日志观察边缘场景；之后从小流量灰度开始，逐步扩大覆盖面，并配合对账、告警和应急预案，确保迁移过程中任何异常都能被及时发现和快速回滚。

整体收益上，业务侧最直观的感受是：新玩法建设效率明显提升、策略迭代节奏拉快，能更高频拿到可靠的 ROI 数据；研发侧，通用组件和能力沉淀下来，新接入一个玩法不再从零造轮子；稳定性侧，通过统一协议、统一链路和完善的迁移/灰度机制，把体系级改造的风险控制在一个可接受的范围内。

如果面试岗位偏业务后端，我会强调两点：第一，能够深入业务理解真正的瓶颈，不是简单堆功能，而是识别出“体系问题”；第二，能把这种体系问题拆成工程化方案，在协议、链路和架构三个层面落地，并且兼顾效率和稳定性，帮助业务“跑得更快但不更脆”。
