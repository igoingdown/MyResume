# 商城增长与稳定性经验 - Agent 研发工程师 5min 版本

如果岗位偏 Agent 研发或智能应用研发，我会用增长框架和稳定性工程化这两个项目，来映射说明我如何把一个高不确定性的系统，做成可观测、可评测、可灰度和可回滚的工程化产品。

先从本质上对齐一下：Agent 系统的难点不在于能不能跑通一个 demo，而在于当你接入很多 tool、在真实业务场景里高频调用时，如何控制复杂度和风险。这和增长玩法体系、规则引擎、配置平台其实是同构问题：都是“高频变化 + 强编排 + 结果不完全确定”的系统。

在增长框架项目中，我做的三件关键事，对 Agent 研发非常有借鉴意义：统一协议与插件化、路由与决策、观测与评测闭环。

第一，统一协议与插件化。增长玩法里，每个区块、组件本质上就是一个“能力插件”，我通过统一的数据协议和组件接口，把这些能力抽象成可以自由组合的模块。对应到 Agent，就是我们把外部系统、工具和内部服务抽象成一类类 tool/skill，定义清晰的输入输出 schema 和错误语义，让大模型在调用这些工具时有一个稳定的约定。在增长项目中，我通过“页面 + 区块”的统一协议，让新玩法接入不需要从头到尾定制协议，而是在统一协议下扩展；同理，在 Agent 系统里，我也会优先设计好工具层的协议和封装，让 LLM 只需要在一个规范的接口面上做选择和组合。

第二，路由与决策。增长体系中的规则引擎，其实就是一个“有限策略空间里做决策与裁决”的系统。我们有不同人群、实验、时间窗口、优先级和自定义因子，这本质上是一个多维条件下的路由问题，和 Agent 在多个 tool、multiple step plan 之间做决策非常像。我在增长框架里把“防配错”和“冲突可控”当成一等公民，通过规则模型、冲突检测、优先级裁决和预览机制来保证决策可解释、可回滚；如果映射到 Agent，我会重点做两层事情：一层是 prompt/策略的版本化和灰度，确保我们对每次决策逻辑的变化是有记录、有对比、有回滚点的；另一层是对多工具调用链路的约束和裁决规则，比如对幂等性、一致性、安全操作做明确建模，避免 Agent 任意组合导致“不可预知的副作用”。

第三，观测与评测闭环。在稳定性项目里，我做的是“问题前移 + 统一观测 + 压测可信”；在 Agent 场景里，对应的是 trace、评测和回放。我会把每一次 tool 调用、每一个关键决策步骤都打点记录下来，形成完整的调用链；结合离线评测集和在线 A/B 实验，驱动策略和 prompt 的迭代；同时对高风险操作（比如涉及真实资产、配额、写入型操作）设置 guardrail 和审批机制，用类似我们在规则引擎里做审计和快速回滚的方式来保护系统安全。

我还会强调一点：在这两个项目中，我非常强调“灰度和回滚”这两个工程特性。无论是统一协议改造、还是稳定性策略升级，我都坚持用小步灰度、完整监控和清晰回滚点的方式去落地，而不是一次性上线。这种工程习惯，对 Agent 系统特别重要，因为 Agent 的输出具有不确定性，一旦出问题，如果没有完整的观察、评测和回滚体系，很难快速止损。

总结一下，如果从 Agent 研发岗位看我这段经历，我可以提供的价值主要有三点：第一，能把高不确定性、高复杂度的决策系统拆成“协议/工具层 + 决策层 + 治理层”的可实现结构；第二，习惯从观测、评测、灰度和回滚的角度设计系统，让 Agent 从 PoC 走向生产可控；第三，有实际在大流量、电商场景下做工程化上线的经验，知道在真实业务环境中要优先解决什么问题，而不是只做“实验室里的漂亮 demo”。
