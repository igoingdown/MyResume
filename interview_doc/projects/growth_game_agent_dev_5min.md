# 商城增长与稳定性经验 - Agent 研发工程师（5min 讲述 + 追问 ≤10min）

> 时间控制：讲述 5–6 分钟 + 追问 3–4 分钟，总计不超过 10 分钟。

## 背景（~45s）

我主要做电商后端，做过两个与 agent 系统特征“高不确定性/高频变化/高复杂度”相似的系统建设：一是商城增长玩法的统一框架（配置化、规则引擎、流程编排引擎），二是营销中台 B&C 链路的工程化稳定性治理（观测、灰度、降级、回滚、压测置信度治理）。

这两个项目跟 Agent 开发有明显相通的地方：Agent 的核心难点并不是“能跑通 demo”，而在于实际生产环境中 llm 的不稳定性、大量的 tool call、多轮对话引入的状态管理和状态转移的复杂性。工程上的解决思路很接近：通过充分的稳定性保障对上游屏蔽不稳定性，通过抽象和系统设计，将复杂度关在系统边界里，让系统整体具备可观测、可评测、可灰度、可重试、可回滚、可降级的基础能力。

## 思路（~45s）

我做这类系统的通用方法是“三层收敛”，先把不确定性结构化：

1. **协议/工具层**：把能力抽象成可组合的 tool/skill/component，用稳定 schema 和错误语义把边界钉死。
2. **决策/编排层**：把路由、优先级、冲突与兜底做成确定性裁决（deterministic），保证可解释与可回滚。
3. **治理/闭环层**：把 trace、评测、灰度、降级、预览、回放与审计内建为默认能力，并在每次迭代中重点 review，保证可控迭代。

## 解决方案（~2m30s）

### 1）协议与插件化（工具层）

在增长框架里，每个区块/组件本质就是一个“能力插件”。我通过统一的数据协议 + 组件接口，把页面承接变成“可组合的能力集合”，新玩法更多是在统一协议下扩展，而不是重新定一套交互。

映射到 Agent，我会优先把外部系统与内部服务标准化成 tool，并把这些元信息写清楚：

- **输入输出 schema**：字段类型、约束、必填、默认值。
- **错误语义**：可重试/不可重试/需人工介入；失败原因分类。
- **副作用声明**：是否写入、是否幂等、是否可回滚、是否可重试、是否有降级方案、是否需要审批。

这样做的目的，是把复杂度收敛在工具层与适配层，让模型面对的是“规范工具集合”，而不是把系统细节塞进 prompt。

### 2）路由与决策（编排层）

增长体系里的规则引擎，本质是“多维条件下的决策与裁决”：人群、实验、时间窗口、优先级、自定义因子叠加后很容易冲突与爆炸，真正难点是让线上行为确定、可解释、可回滚。

映射到 Agent，我会把“选择哪个工具、走哪条链路、何时兜底”当成一等公民：

- **路由可解释**：每次选择输出结构化证据（命中的规则/特征、候选评分、成本与时延预估、选择原因、兜底条件）。
- **版本化与灰度**：prompt/策略/路由规则全部版本化，一个版本就是一整套产品能力+一整套的业务策略，基于版本跑 bench+小流量灰度 + 指标护栏 + 一键回滚。
- **冲突与边界**：对多工具链路引入裁决规则（优先级、互斥、前置校验），避免工具任意组合造成副作用扩散。

### 3）观测与评测闭环（治理层）

稳定性治理里我强调“问题前移 + 统一观测 + 压测可信”，映射到 Agent 主要是 trace、评测与回放：

- **全链路 trace**：记录每次 tool call 的输入/输出摘要、耗时、重试、失败原因、兜底路径。
- **离线评测 + 在线灰度**：离线用基准集/回放做回归，在线用 A/B 验证增量效果，形成闭环迭代。
- **高风险 guardrail**：对写入型/不可逆操作加权限边界、审批/双确认、审计溯源与熔断。

## 亮点与难点（~1m30s）

### 亮点

- 我擅长把“高不确定性系统”工程化成可交付系统：可观测、可评测、可灰度、可回滚，而不是停留在 PoC。
- 我在增长/稳定性里长期处理“大流量 + 高变更 + 多团队协作”，习惯把治理能力前置，避免系统后期失控。

### 难点

1. **抽象边界难**：schema 既要稳定又要可扩展，避免协议变成“万能胶”。
2. **确定性裁决难**：冲突/优先级/兜底要 deterministic，否则线上行为不可解释，也不可复现。
3. **评测可信度难**：离线评测与线上指标要对齐，避免“离线好看、线上翻车”。

## 可追问的问题及答案（3–4min，建议挑 3–5 个讲）

### Q1：你会如何设计 Agent 的 tool schema 与错误语义？

A：我会把工具元信息做成“可机器读取”的规范：输入输出 schema + 错误分类（可重试/不可重试/需人工介入）+ 幂等与副作用声明（写入/可回滚/审批）。路由层和评测层都复用这份规范。

### Q2：如何做 Agent 评测，避免只在 demo 上有效？

A：离线 + 在线两套：离线用基准集回放与回归（确保不退化），在线用灰度 A/B 看真实指标（成功率、成本、时延、风险事件）。两者共享 trace 数据，能把失败分型并驱动改进。

### Q3：多工具调用时如何防止策略爆炸、不可控副作用？

A：用裁决规则收敛：互斥/优先级/前置校验 + 兜底链路；对高风险工具加 guardrail（权限、审批/双确认、限速、熔断）。同时策略版本化，任何变更走灰度与一键回滚。

### Q4：某个 tool 不稳定（超时/错误率高），Agent 如何兜底？

A：先分错误类型制定重试策略（超时/限流/业务错误分开），再降级（替代工具、缩短链路、返回可解释的中间结果），最后熔断与回滚（指标触发自动切换安全路径），并保留可回放样本用于修复。

### Q5：你说“路由可解释”，具体怎么落地？

A：让路由输出结构化“决策证据”：命中条件、候选工具得分、成本/时延估计、选择原因、兜底条件，并写入 trace。线上复盘时能回答“为什么这次走了这条链路”。

### Q6：你强调灰度与回滚，落到 Agent 的发布流程会是什么样？

A：把 prompt、路由策略、工具版本都当成可发布对象：版本化 + 小流量灰度 + 指标护栏 + 一键回滚；并配合离线回放评测，确保回滚回到“已验证稳定版本”，而不是回到未知状态。
